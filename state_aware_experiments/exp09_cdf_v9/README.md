# exp09 — Real-CDF workload filter comparison

## Motivation

**exp07 and exp08 both produced null results — for opposite reasons:**

| Experiment | Load | ECN rate | Filter signal | Result |
|---|---|---|---|---|
| exp07 | Full bisection (128 flows) | 3–15% of ACKs | Diffuse (65% at counter≥4) | No improvement |
| exp08 | Sparse (2–32 flows) | 0% | None | No improvement |

Both used **synthetic permutation traffic** — uniform random src→dst pairs, identical flow sizes. The "outlier-EV" regime required for filters to work (sparse ECN localized to specific EVs) never arises in these workloads: at low load there's no congestion, and at high load congestion is global.

**Hypothesis**: real datacenter traffic CDFs have heavy-tailed flow size distributions. Elephant flows create sustained bottlenecks on specific paths, while mice flows transit freely. This may produce the localized congestion that exp07/08 lacked.

**Question**: Does CDF-based traffic (WebSearch, Hadoop) produce non-zero, non-diffuse ECN in this simulator? If so, does any filter mechanism improve FCT?

## Results

### Phase 1 — Discovery probe (24 cells, vanilla only)

#### Headline: WebSearch l=90 has ECN; Hadoop has none at any load

| Workload | Load | Sev | Mean n_ecn_acks | high_counter_rate | Proceed? |
|---|---|---|---|---|---|
| WebSearch | 30% | 0/4 | 0 | — | No |
| WebSearch | 60% | 0/4 | 0 | — | No |
| WebSearch | 90% | 0 | 260 (min=0, max=519) | 0.021 | **Yes** |
| WebSearch | 90% | 4 | 678 (min=0, max=1356) | 0.164 | **Yes** |
| Hadoop | all | all | 0 | — | No |

**Phase 1 decision**: Proceed to Phase 2 for **WebSearch only**. Hadoop has zero ECN at all tested loads (30–90%) — the tiny-flow-dominated workload (mean Hadoop flow ≈ 5 KB) does not sustain queues above the 25% ECN threshold on this fat-tree. This is itself an informative finding.

**Critical Phase 1 finding**: WebSearch l=90 `high_counter_rate` = **0.02–0.16**, far below exp07's baseline of 0.65. This means when ECN does fire in the CDF workload, only 2–16% of ECN ACKs arrive with an already-high counter — the congestion IS spatially localized (outlier-EV regime). The smart-filter mechanisms should have a real signal to act on.

**Caveat**: High seed-to-seed variance at l=90. One seed shows 519 ECN ACKs, the other shows 0 (sev=0). This is expected for Poisson-arrival CDF traffic: the heavy-tail nature means some runs have large flows co-located on the same path (congestion) and others do not. Phase 2 uses 3 seeds to average over this.

#### Flow completion summary (Phase 1)

| Workload | Flow class | Count | Mean slowdown | p99 slowdown |
|---|---|---|---|---|
| WebSearch | mice (<100KB) | 47,963 | 3.79× | 11.84× |
| WebSearch | medium (100KB–10MB) | 31,936 | 2.37× | 8.69× |
| WebSearch | elephant (>10MB) | 7,620 | 1.42× | 4.80× |
| Hadoop | mice | 1,731,455 | 3.86× | 9.52× |
| Hadoop | medium | 222,615 | 3.22× | 11.76× |

High slowdowns for mice flows are expected: ideal FCT for a tiny flow is just the base RTT (4µs), any queueing or cwnd buildup adds a multiple. The absolute FCT difference is small.

### Phase 2 — Full filter comparison (144 cells, WebSearch only)

#### Headline: No filter improves FCT; evhealth modes regress significantly

**p99 FCT slowdown at WebSearch l=90 (mean ± std across 3 seeds):**

| Mode | sev=0 p99 | sev=4 p99 | vs vanilla |
|---|---|---|---|
| vanilla | 11.62 ± 0.31 | 11.62 ± 0.14 | — |
| wtd | 11.66 ± 0.43 | 11.81 ± 0.18 | neutral |
| sf_md_gain_ecn | 11.59 ± 0.31 | 12.29 ± 0.60 | neutral / slight ↑ sev=4 |
| sf_md_gain_fresh | **11.34 ± 0.41** | 11.82 ± 0.41 | best mode at sev=0 |
| sf_blend_ecn | 12.02 ± 0.37 | 12.31 ± 0.37 | ↓ worse |
| sf_blend_fresh | 11.70 ± 0.26 | 11.94 ± 0.27 | neutral |
| sf_md_gain_evhealth | 13.79 ± 0.37 | 14.24 ± 0.51 | **↓↓ significant regression** |
| sf_blend_evhealth | 14.57 ± 0.44 | 14.68 ± 0.66 | **↓↓ significant regression** |

**Mean FCT at WebSearch l=90 (µs):**

| Mode | sev=0 | sev=4 |
|---|---|---|
| vanilla | 108.3 ± 1.9 | 109.0 ± 2.1 |
| wtd | 108.0 ± 2.2 | 109.2 ± 3.0 |
| sf_md_gain_ecn | 108.6 ± 2.1 | 109.7 ± 2.3 |
| sf_md_gain_fresh | 108.2 ± 2.6 | 109.3 ± 2.5 |
| sf_blend_ecn | 108.9 ± 2.1 | 110.2 ± 2.8 |
| sf_blend_fresh | 108.0 ± 1.8 | 109.2 ± 1.8 |
| sf_md_gain_evhealth | 111.4 ± 2.6 | 112.3 ± 2.4 |
| sf_blend_evhealth | 113.2 ± 2.3 | 113.9 ± 2.9 |

#### Finding 1: Standard filter modes are neutral

WTD, `sf_md_gain_ecn`, `sf_md_gain_fresh`, `sf_blend_fresh` all produce FCT within noise of vanilla. This holds at all loads (l=30, l=60 have zero ECN; l=90 has sparse ECN). The null result extends across all three load regimes in CDF traffic.

#### Finding 2: evhealth counter causes significant regressions (+2–3 slowdown units)

Both `sf_md_gain_evhealth` and `sf_blend_evhealth` regress substantially: p99 slowdown +2.2 to +3.0 units above vanilla, mean FCT +3–5 µs. This is the most impactful (negative) finding in exp09.

**Root cause — evhealth "dirty state" persistence**: The evhealth counter (`SF_COUNTER_EVHEALTH`) tracks whether each EV currently in the REPS buffer had its *last* ACK ECN-marked. Once an EV receives an ECN mark, `_ev_last_ecn_state[ev] = 1` and stays 1 until that specific EV receives a *clean* ACK. At WebSearch l=90 with sparse ECN:

1. A single ECN event marks one EV as "bad" → `_ecn_buffer_counter ≥ 1`
2. Mode A scales MD by `counter/B = 1/8` → only 12.5% of normal MD
3. The flow fails to back off sufficiently → cwnd stays too high → queue builds up → more ECN
4. The EV's dirty state persists until that specific EV gets another ACK (potentially many RTTs)
5. Self-reinforcing loop: mild MD → sustained high cwnd → more ECN ACKs from that EV

Evidence: evhealth modes show **2–5× more n_ecn_acks** than vanilla (328–850 vs 173–452), confirming the cwnd feedback loop. WTD block rate = 0 for all 3 seeds at sev=0 (the 1 seed with no ECN never fires WTD either).

#### Finding 3: Sparse localized ECN ≠ sufficient filter signal

The evhealth counter WAS the right architectural idea — it measures the signal directly (which specific EVs are persistently congested). The problem is the "last-seen" design creates a slow-draining dirty state. A correct design would need either:
- A time-decayed dirty state (`_ev_last_ecn_state[ev] *= decay_factor` on clean ACKs)
- A counter that requires N consecutive ECN ACKs from the same EV to mark it bad

#### ECN counter statistics at l=90

`high_counter_rate` (fraction of ECN ACKs where counter ≥ B/2):
- vanilla: 0.014 (sev=0), 0.109 (sev=4) — confirms sparse, localized ECN
- evhealth modes: 0.000 — because the evhealth counter is always < 4 (at most a few EVs are bad at once in sparse-ECN regime); paradoxically, evhealth *finds* the localized signal but uses it destructively

#### WTD at CDF load

WTD block rate = 0 in 2/3 seeds (those with no ECN). In the seed with ECN (seed 42), block rate = 0.26 (sev=0) and 0.39 (sev=4). No FCT benefit despite occasional MD blocking — consistent with exp07/08.

#### Comparison across all three experiments

| Experiment | Load | ECN rate | ECN type | Filter benefit |
|---|---|---|---|---|
| exp07 | Full bisection (perm) | 3–15% ACKs | Diffuse (65% at counter≥4) | None |
| exp08 | Sparse (perm, 2–32 flows) | 0% | None | None |
| exp09 l=30,60 | Medium (CDF) | 0% | None | None |
| exp09 l=90 | High (CDF) | 5–15% ACKs in ECN seeds | **Localized (hcr<0.15)** | None (evhealth: negative) |

The full progression: congestion is either too diffuse, too absent, or too sparse-and-localized. In the one regime where the architecture has signal (localized ECN at l=90), the counter design prevents MD from working correctly, causing regressions instead of improvements.

#### Conclusion

**Null result with an important negative finding**: No NSCC ECN filter mechanism improves FCT under real CDF (WebSearch) traffic in this simulator. The evhealth counter, despite measuring the correct signal (which specific EVs are congested), causes significant p99 regression (+18–25%) due to its "sticky dirty state" that under-weights MD after ECN events. The `fresh` counter (Mode A: `sf_md_gain_fresh`) shows the mildest downside at sev=0 (p99 −2.4% vs vanilla) but is not significant given seed variance.

**Architectural implication**: The filter placement between LB and CC is sound, but the counter design for a "persist-until-clean" evhealth signal is flawed. A time-decayed version could be explored in a future experiment.
