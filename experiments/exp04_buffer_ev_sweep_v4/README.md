# exp04 — Buffer Size & EV Domain Sweep

**Status**: **Complete.** 400 runs, 10934s wall time (~3h). Full artifacts preserved.

---

## Motivation

exp03 used REPS FREEZING with its default 8-slot buffer and a 65535-entry EV domain. This experiment isolates two orthogonal REPS design axes to understand their effect on both **load balancing quality** and **NSCC congestion control behaviour**:

1. **Part A — Buffer size sweep**: how the bounded FREEZING buffer capacity affects path diversity and CC aggressiveness.
2. **Part B — EV domain sweep**: how many distinct physical paths REPS can choose from.

Core question: does restricting either axis force the CC to be overly conservative (cwnd ≪ BDP), or is any underutilisation benign (flow near completion, light load)?

---

## Topology

- **fat_tree_128_1os_3t_400g.topo** — k=8, 128 hosts, 400 Gbps links, 3-tier, 1:1 OC
- Full ECMP domain: (k/2)² = **16 distinct cross-pod paths**
- BDP reference: 400 Gbps × 4 µs RTT / (8 × 4150 bytes) ≈ **48 packets**

---

## Design Matrices

### Part A — Buffer size sweep (200 runs)
- `buf` ∈ {1, 2, 4, 8, **1024≈∞**}; fixed `-paths 16` (full EV domain)
- `sev` ∈ {0, 4}; `workload` ∈ {pureperm_8mb, composite, perm_32mb, perm_128mb}; `seed` ∈ {42–46}

### Part B — EV domain sweep (200 runs)
- `ev_domain` ∈ {1, 2, 4, 8, **16=full**}; fixed `-reps_buffer_size 1024`
- Same `sev`, `workload`, `seed` as Part A

**Total**: 400 runs. Always vanilla FREEZING (no `-state_aware_ecn`).

|---|---|---|---|

### `pureperm_8mb` — baseline permutation matrix

**File**: `connection_matrices/perm_n128_s8388608.cm` (fixed — not seed-parameterised)

- **128 flows**, one per host. Every host sends to exactly one other host; every host receives from exactly one sender — a strict bijective permutation.
- **All flows start at t=0** simultaneously.
- **Flow size**: 8 MB (8,388,608 bytes) each. Ideal FCT ≈ 167.8 + 4.0 = **171.8 µs**.
- **Full bisection by construction**: each flow crosses pod boundaries, saturating bisection links immediately at t=0.
- The TM is fixed (no seed variation across the 5 seeds) — seed only affects REPS entropy selection.

### `perm_32mb` — medium-load permutation matrix (seed-parameterised)

**Files**: `connection_matrices/perm_128n_128c_32MB_s{42..46}.cm`

- **128 flows**, strict permutation. A different random permutation per seed (5 distinct TMs).
- **All flows start at t=0** simultaneously.
- **Flow size**: 32 MB (33,554,432 bytes) each. Ideal FCT ≈ 671 + 4.0 = **675 µs**.
- **Full bisection**: same structure as `pureperm_8mb` but 4× larger flows; the network stays under load for ~4× longer.
- Seed variation here covers both different permutations *and* different REPS entropy sequences.

### `perm_128mb` — heavy full-bisection stress (seed-parameterised)

**Files**: `connection_matrices/perm_128n_128c_128MB_s{42..46}.cm`

- **128 flows**, strict permutation. A different random permutation per seed.
- **All flows start at t=0** simultaneously.
- **Flow size**: 128 MB (134,217,728 bytes) each. Ideal FCT ≈ 2684 + 4.0 = **2688 µs ≈ 2.7 ms**.
- **Simulation ends at t=5000 µs** — under ideal conditions flows finish at ~2.7 ms, leaving ~2.3 ms headroom. Under congestion (ev_domain=1 with sev=4) many flows fail to complete within the 5 ms window (`n_flows_finished` < 128 is expected and reported).
- This is the **most discriminating workload**: it keeps the bisection saturated for nearly the entire simulation, making it sensitive to any LB degradation (wrong path, congested path) or CC suppression.

### `composite` — mixed-class realistic workload

**File**: `experiments/workloads/composite.cm` (fixed, generated by `gen_composite.py`)

416 flows in three classes, with different sizes, start times, and traffic patterns:

#### Class 1 — Elephants (flow IDs 1–96, 96 flows)

- **Size**: 8 MB (8,388,608 bytes) each. Ideal FCT ≈ **172 µs**.
- **Start time**: all at **t=0**.
- **Topology**: 96 randomly chosen (src, dst) pairs (RNG seed 20). Not a permutation — some hosts may send or receive multiple elephant flows simultaneously. Self-loops are avoided.
- **Role**: provides immediate bisection load from the start. Most elephants finish between t≈200–400 µs (slower than ideal due to competing with each other).

#### Class 2 — Mice (flow IDs 97–352, 256 flows)

- **Size**: 32 KB (32,768 bytes) each. Ideal FCT ≈ 0.66 + 4.0 = **4.66 µs** (dominated by propagation delay).
- **Start time**: staggered across **16 waves of 16 flows each**:

  | Wave | Start time | Flow IDs |
  |---|---|---|
  | 0  | t = 10 µs  | 97–112  |
  | 1  | t = 35 µs  | 113–128 |
  | 2  | t = 60 µs  | 129–144 |
  | 3  | t = 85 µs  | 145–160 |
  | 4  | t = 110 µs | 161–176 |
  | 5  | t = 135 µs | 177–192 |
  | 6  | t = 160 µs | 193–208 |
  | 7  | t = 185 µs | 209–224 |
  | 8  | t = 210 µs | 225–240 |
  | 9  | t = 235 µs | 241–256 |
  | 10 | t = 260 µs | 257–272 |
  | 11 | t = 285 µs | 273–288 |
  | 12 | t = 310 µs | 289–304 |
  | 13 | t = 335 µs | 305–320 |
  | 14 | t = 360 µs | 321–336 |
  | 15 | t = 385 µs | 337–352 |

  **Inter-wave spacing**: 25 µs (much longer than the ~5 µs ideal FCT, so waves don't overlap if the network is healthy).
- **Topology**: uniformly random (src, dst) pairs. Not a permutation.
- **Role**: latency-sensitive short flows. FCT slowdown is the key metric; a congested network inflates their FCT by delaying the first ACK.

#### Class 3 — Incast (flow IDs 353–416, 64 flows)

- **Size**: 2 MB (2,097,152 bytes) each. Ideal FCT per flow ≈ 41.9 + 4.0 = **45.9 µs** in isolation.
- **Start time**: all **64 flows start simultaneously at t=80 µs** (overlapping with mice wave 3 at t=85 µs).
- **Topology**: 4 victim hosts (nodes 3, 41, 77, 119), each receiving from 16 dedicated senders simultaneously. The 16 senders for victim `v` are nodes `(v+1+offset) % 128` for offset 0..15. Each victim is in a different pod of the k=8 fat-tree.
- **Role**: creates a sudden 16:1 fan-in at 4 specific ToR switches at t=80 µs — the scenario most likely to trigger queue buildup and ECN. The incast arrives while elephants are mid-flight, creating realistic co-existing congestion.

#### Composite timeline summary

```
t=0        Elephants start (96×8MB) — bisection fills immediately
t=10 µs    Mice wave 0 (16×32KB)
t=35 µs    Mice wave 1
t=60 µs    Mice wave 2
t=80 µs    *** INCAST starts (64×2MB, 16:1 fan-in at 4 victims) ***
t=85 µs    Mice wave 3 (concurrent with incast)
...
t=172 µs   First elephants finish (ideal FCT)
t=385 µs   Last mice wave (wave 15)
t~200-400  Most elephants finish
t~5000 µs  Simulation end
```

`perm_32mb` and `perm_128mb` use seed-parameterised TMs (different permutations per seed).

**Note on `perm_128mb` completion**: flows take ~2.7 ms at line rate in a 5 ms simulation. Under severe congestion (buf=1 or ev_domain=1 with sev=4), some flows may not complete — `n_flows_finished` is reported and should be interpreted accordingly.

## Metrics

### FCT metrics
- p50, p99 FCT per flow class
- **FCT slowdown** = `fct_us / ideal_fct_us` where `ideal_fct_us = flow_size×8/400Gbps + 4µs`  
  Normalises out flow-size differences; slowdown=1.0 = perfect.

### CC window metrics (from `reps_state.csv`, src 0 per run)
| Metric | Formula | Interpretation |
|---|---|---|
| `cwnd_bdp` | cwnd_pkts / 48 | CC window as fraction of 1 BDP |
| `fill_rate` | in_flight_pkts / cwnd_pkts | How well the window is being used |
| `net_fill` | in_flight_pkts / 48 | Fraction of pipe occupied |

> `cwnd_bdp < 1` + `fill_rate ≈ 1` → **CC is the bottleneck** (window too small)  
> `cwnd_bdp < 1` + `fill_rate < 1` → **benign underutilisation** (light load / flow near end)

## Findings

### Part A — Buffer size sweep (key results)

**FCT p99 slowdown is nearly flat across all buffer sizes.**

| buf | pureperm_8mb sev=0 | pureperm_8mb sev=4 |
|---|---|---|
| 1 | 1.363× | 1.823× |
| 2 | 1.343× | 1.824× |
| 4 | 1.331× | 1.847× |
| 8 | 1.337× | 1.797× |
| ∞ (1024) | 1.353× | 2.084× |

- **Verdict**: Buffer size does not materially affect FCT in this topology/workload. The 8-slot default is sufficient; even buf=1 performs comparably. Interestingly, buf=∞ has slightly *worse* p99 at sev=4 — a larger buffer may allow REPS to continue using a stale EV for longer after a failure.
- **All 128MB flows complete** across all buffer sizes including buf=1 at sev=4.

**CC window is insensitive to buffer size.**

- Mean cwnd/BDP ≈ **4.3** across all buffer sizes and severities — the CC window stays at ~4× BDP regardless of buffer.
- Mean fill_rate ≈ **0.97** (CC is the binding constraint, not data availability). Underutilisation is benign: the window is almost always full, so cwnd is the limiting factor, not ACK starvation.

### Part B — EV domain sweep (key results)

**EV domain has a dramatic effect on FCT and flow completion.**

| ev_domain | pureperm_8mb sev=0 | pureperm_8mb sev=4 | perm_128mb sev=4 completions |
|---|---|---|---|
| 1 (single path) | 5.00× | 4.53× | **45/128** |
| 2 | 2.82× | 2.98× | 97.2/128 |
| 4 | 2.04× | 2.60× | 126.4/128 |
| 8 | 1.63× | 2.38× | 128/128 |
| 16 (full) | 1.35× | 2.08× | 128/128 |

- **Verdict**: EV domain is the critical design parameter. A single-path domain causes 5× FCT inflation even without any failure, and only 45/128 heavy flows complete under sev=4. Diminishing returns set in around 8 paths.
- The improvement from 1→2→4 paths is large; 8→16 is modest. For this k=8 topology, **ev_domain=8** captures most of the benefit.

**CC window is suppressed by narrow EV domain.**

- Mean cwnd/BDP: **partA ≈ 4.34** vs **partB ≈ 3.81** (infinite buffer, but constrained paths causes more ECN → lower cwnd).
- With ev_domain=1, cwnd/BDP drops further (all flows compete on one path → high ECN rate → CC backs off hard).
- **Fill_rate ≈ 0.97–0.99** in all cases (post-artifact cleanup): the CC window is always nearly full, confirming CC conservatism is the bottleneck, not flow completion or ACK starvation.

### Data quality note

Two rows in `v4_cwnd.csv` (out of 4.4M) show `in_flight_pkts = 2^32 - 1` — a momentary integer underflow when `_in_flight` briefly goes negative (e.g. during RTO) and is cast to `unsigned`. These 0.00004% of rows are capped to `fill_rate = 2.0` in the plotter and have no effect on any aggregate metric.
