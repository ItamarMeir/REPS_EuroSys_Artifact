# exp08 — Low-load filter comparison

## Motivation

**exp07 was a null result**: no filter mode (WTD, Mode A, Mode B with ECN/fresh counter) improved FCT over vanilla at full bisection load (128 concurrent flows). Two root causes were identified:

1. **Load too high for spatial separation**: 65% of ECN-marked ACKs arrived with `ecn_counter ≥ 4/8`. Congestion was diffuse and global, not localized to outlier EVs. The filter premise — "some EVs congested, most clean" — didn't apply.
2. **Fresh counter was useless**: `fresh_inv = B − fresh` was stuck near 8 for 98% of ACKs because REPS depletes all 8 fresh buffer slots immediately.

This experiment addresses both problems:
- **Low load** (2, 16, 32 concurrent flows) — where the network is mostly idle and ECN events are expected to be spatially concentrated on the one or two flows that happen to share a congested path.
- **EV-health counter** (`-smart_filter_counter evhealth`) — a new counter (implemented in the code before this experiment was run) that tracks how many EVs currently in the REPS buffer have had their last ACK ECN-marked. This measures the "outlier-EV" signal directly: 0 means all buffer EVs are healthy, 8 means all are congested.

## EV-health counter — what it does

`SF_COUNTER_EVHEALTH` (`sf_counter_used=2`) maintains a per-EV last-ECN-state vector `_ev_last_ecn_state[]` of size `_no_of_paths`. On each ACK, it:
1. Sets `_ev_last_ecn_state[pkt.ev()] = (ecn ? 1 : 0)`.
2. Calls `circular_buffer_reps->getValidEntropies()` to get the ≤ B EVs currently in the buffer.
3. Counts those with `_ev_last_ecn_state[ev] == 1`.
4. Stores the count in `_ecn_buffer_counter` (same field logged as `ecn_counter` in the CSV).

Complexity: O(B²) = O(64) per ACK. Compatible with both Mode A (md_gain) and Mode B (rtt_blend_ecn_thresh).

## Results

### Headline: Zero ECN at all tested load levels — null result, deeper root cause found

**n_ecn_acks = 0 for every source across every workload, sev, seed, and mode.**
Not a single ECN-marked ACK was logged by the 3 diagnostic sources (0, 1, 7) in any of the 240 runs.

All filter modes (vanilla, WTD, all smart-filter variants including evhealth) produce **byte-identical FCT distributions**. p99 FCT slowdown is 1.064–1.089 for all modes, driven entirely by normal CWND dynamics, not by ECN congestion control.

### Why: The ECN marking threshold is not reached at sparse load

The simulator uses ECN low threshold at 25% of queue size (`-ecn 25 76`). At ≤ 32 concurrent flows on a 128-host 400Gbps fat-tree, the network is massively underloaded: flows get full-bandwidth paths and queues never approach the 25% marking threshold. There is simply no ECN to filter.

**Comparison with exp07 (full bisection = 128 flows):** ECN appeared in 3.8–15% of ACKs per source, with 65% of those ECN events at `ecn_counter ≥ 4`. Even at full bisection, ECN was not the dominant factor in FCT (it was diffuse). At 32 flows (25% of full bisection), ECN disappears entirely.

### FCT summary (vanilla, all seeds pooled)

| Workload | Sev | Mean FCT | p99 slowdown | n_ecn_acks (3 sources) |
|---|---|---|---|---|
| perm_2c_8mb | 0 | 182.8 µs | 1.065 | 0 |
| perm_2c_8mb | 4 | 183.1 µs | 1.070 | 0 |
| perm_16c_8mb | 0 | 183.2 µs | 1.080 | 0 |
| perm_16c_8mb | 4 | 183.4 µs | 1.086 | 0 |
| perm_32c_8mb | 0 | 183.7 µs | 1.085 | 0 |
| perm_32c_8mb | 4 | 183.9 µs | 1.089 | 0 |

Ideal FCT = 171.8 µs. The ~11 µs gap is queue-induced delay at sender startup — not ECN-driven.

### WTD at low load

WTD block rate = 0.0 for all seeds/workloads/severities. With no ECN ACKs, the gate never fires. This conclusively settles the exp07 question: WTD's high block rate at full bisection (0–100% variance) was not a transient issue — it requires ECN to be present. At low load, WTD is an exact no-op.

### EV-health counter at low load

`ecn_counter = 0` for all evhealth runs (correct: no ECN-marked ACKs means no bad EVs). The evhealth counter is correctly wired — it simply has nothing to count. FCT is identical to vanilla.

### Freezing events (sev=4)

The link failure still injects freezing entries:
- perm_2c_8mb/sev4: 1–3 flows start freezing per run (2 flows, ~2 paths at risk)
- perm_16c_8mb/sev4: ~3–5 flows freeze per run
- perm_32c_8mb/sev4: ~5–9 flows freeze per run

These show the failure injection is working and REPS is detecting path loss via RTO. The flows recover without visible FCT impact because the freeze duration (exit_freeze=200ms) is much longer than the failure window (150µs), so frozen flows simply wait for the automatic REPS unfreeze.

### Conclusion: Load floor for filter relevance is above 32 concurrent flows

All three experiments (exp06, exp07, exp08) converge on the same answer: **the NSCC ECN filter mechanism has no leverage** in this simulator's parameter space. The mechanisms are correctly implemented — the null result is informative, not a bug:

| Condition | ECN present? | Filter has signal? | FCT impact |
|---|---|---|---|
| Full bisection, 128 flows (exp07) | Yes (3–15% of ACKs) | No — ECN is diffuse (65% at `counter≥4`) | No improvement |
| Low load, 32 flows (exp08) | No | No — nothing to filter | No improvement |

**The gap**: the "outlier-EV" regime (sparse ECN localized to one congested path) does not naturally arise in these permutation workloads. It would require either: (a) intentional hot-spot traffic (e.g., many-to-one incast where senders share a bottleneck link), or (b) asymmetric topologies where one route is persistently worse than others.
