# C3 - does the buffer-size result survive a bursty (not always backlogged) sender?

(Originally numbered C4. The first C3, "scale B up to 256", was dropped because C2's B ladder already runs 1 to 256.)

## Question
C1 and C2 use senders that are always backlogged. Chen Avin's point (2026-10-06): a sender that pauses may let clean ACKs accumulate in the buffer, which could make a large B useful. C3 tests that: when a sender pauses and resumes, how full is the buffer at the start of each burst, and does that change FCT or the EVs drawn?

## Setup
- Healthy fabric `fat_tree_1024_1os_2t_400g`, tornado, **NSCC**, trim ON (exp30 trim-on base), `-load_balancing_algo freezing -use_srv6 -paths 32`, seeds 42, 43, 44, B in {1, 2, 4, 8, 16, 32, 64, 128, 256}.
- Only **host 0 is bursty.** Its 16 MiB flow is split into N bursts of 16 MiB / N with a gap between them. `-connections_mapping` makes the N separate flows share one REPS buffer across the gaps. The other 31 ToR0 hosts send one continuous backlogged flow, sized to outlast host 0's whole schedule; hosts 32 to 1023 are byte-identical to C1/C2.
- Four connection matrices (generated by `gen_c3_cm.py`, kept in `htsim/sim/datacenter/connection_matrices/c3_*.cm` with `.schedule.json` sidecars):

| Config | Bursts N | Gap |
|---|---|---|
| `c3_n1_drained` | 1 | none (anchor) |
| `c3_n4_drained` | 4 | 5 RTT (about 41.7 us) |
| `c3_n16_drained` | 16 | 5 RTT |
| `c3_n4_longgap` | 4 | 50 RTT (about 417 us), gap-length control |

4 configs x 9 B x 3 seeds = 108 runs; the trace holds only host 0's rows.
- No simulator change: the generator only edits the connection matrix.

## What is measured
- **Fresh EVs at burst start**: valid buffer entries at the first draw of burst k+1, versus the prediction `min(B, tail)`, where tail = clean ACKs of burst k that arrive after its last plain send (minus competing RTX/RTS draws).
- **Valid-draw decay**: for N = 16, the share of draws that take a valid EV at each send index within a burst.
- **FCT**: total time for host 0 (last finish).
Host state is carried across the change of flow id between bursts (keyed by source address, not flow id), the main pitfall in `analyze_c3.py`.

## Results
- **The buffer does fill during a pause, and the fill is exactly B-limited.** The observed fresh count at burst start equals the prediction `min(B, tail)` in all 63 of 63 boundaries for every B from 1 to 64. The tail is about 113 to 119 clean ACKs. At B = 128 and 256 the buffer holds about 116 to 122 (the prediction is a few entries low: 113 to 119), and B = 128 and 256 are identical because the buffer is bounded by the tail, not by B.
- **The extra valid EVs are used only briefly.** Valid draws occupy only the first B sends of each burst (for B = 8, the first 8 draws are valid and the rest random; for B = 64, the first 64). Around 94% of those initial draws are valid.
- **FCT does not depend on B.** Total host-0 time (mean of 3 seeds, microseconds):

| Config | B = 1 | B = 8 | B = 256 |
|---|---|---|---|
| N = 1 | 357.5 | 356.3 | 356.3 |
| N = 4, 5-RTT gap | 472.1 | 472.0 | 471.8 |
| N = 16, 5-RTT gap | 971.0 | 971.2 | 971.0 |
| N = 4, 50-RTT gap | 1597.3 | 1597.2 | 1597.2 |

  Total time grows with N and with the gap (the pauses themselves), but is flat across B to within 0.4%.
- **Reading.** This contradicts a strict reading of C1's backlog result (few valid EVs): once the sender pauses, B does matter to the *buffer content* (up to about 120 valid EVs after a pause). It does not matter to FCT in this setup, because only the first few draws of a burst benefit and the rest of the burst is paced by the network. C3 therefore limits C1 to "backlogged senders" for the buffer content but not for FCT.

## Caveats
- Host 0 only; other hosts are backlogged, so the fabric stays busy during host 0's pauses. A fully idle fabric is not tested.
- The predicted-fresh formula under-counts by 2 to 5 entries at B >= 128 (5 of 63 boundaries exact); the cause is not investigated.
- 3 seeds, but the FCT differences are far below any plausible CI, so no CI table is given.
- No `RESULTS.md`; the numbers above are read from `data/c3_fct.csv`, `c3_boundary.csv` and `c3_decay.csv`.

## Reproduce
```bash
cd /workspace/experiments/meeting_06_10_26/C3/scripts
python3 gen_c3_cm.py --n 4 --gap-ps 41685600 --out c3_n4_drained   # one per config; gap 5 RTT = 41,685,600 ps, 50 RTT = 416,856,000 ps
python3 run_c3.py --workers 2          # all 108 cells; writes ../runs and ../traces (gzipped)
python3 analyze_c3.py                  # -> ../data/c3_{fct,boundary,decay,checks}.csv
python3 build_c3.py                    # -> ../plots/interactive.html
```
The gaps are 5 x the 8.337 us base RTT (41,685,600 ps) and 50 x (416,856,000 ps); each matrix's `.schedule.json` records the exact burst sizes, gap and background-flow size.
