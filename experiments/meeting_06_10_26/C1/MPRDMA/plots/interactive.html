C1: EV source split, buffer occupancy, FCT -- 16 MiB, MPRDMA

exp30 trim-on configuration, MPRDMA, freezing LB, tornado 16 MiB, trim ON, seed 42, ToR0 hosts (32). Healthy vs all 32 ToR0 uplinks at 50% speed. Split: fractions over all EV draws (new packets + retransmissions); valid + random + stale = 1. Occupancy: fresh = valid buffer entries after each event (from the event trace). Claim: after each host's first ACK, during backlog (before its last send), the buffer holds at most 2 valid EVs. B=1 and 2 are greyed: the buffer cannot hold more than 2, so they cannot test the claim. Send-time k: for every post-warmup SEND/RTX/RTS, k = valid EVs in the buffer immediately before the draw (read from the previous row's post-event fresh count). All 18 cells pass 9 checks (conservation vs the committed per-host finish-line counts, determinism P(k=0)==random share, 0 reconstruction mismatches, stale proven 0, capacity k<=B, sum-to-1, and k<=the independent occupancy.py backlog max). FCT: "finished at" time per ToR0 host (flows start at t~0, so this is the FCT directly), p50/p95/p99/max across the 32 ToR0 hosts. SoL (speed-of-light): a reference arm, path_static+constant (one pinned path per flow, no REPS buffer). It has no buffer, so it does not appear on the split/occupancy/send-time-k/acks-per-window panels -- those measure REPS-buffer-internal behavior that this arm doesn't have. On the FCT panel, each B's FCT is shown normalized against SoL's own FCT (FCT / SoL FCT; 1.0 = speed-of-light floor).
Verified over every post-warmup SEND/RTX/RTS draw of all 32 ToR0 hosts (same population as the send-time-k plot above -- n_sends_post ties out exactly): in healthy, SEND-to-SEND gaps for B≥2 all fall in a tight 83-86.84ns band (0.00% exceed 2x the median); B=1 alone has a small 0.017% tail up to 251.56ns (real cwnd stalls, see the conclusion note). In 32 ToR0 uplinks at 50%, ~24-27% of gaps DO exceed 2x the median (tail up to several μs at every B) -- a real second population, but expected: those uplinks run at half rate, so queueing delay is that scenario's own mechanism, not evidence against the healthy-case claim below. Also verified directly: for every ACK, fresh_after - fresh_before equals +1 if ecn=0 and 0 if ecn=1, with ZERO unexplained mismatches across all 36 cells (both CC) once mismatches caused by the buffer already being at capacity (fresh==B when a clean ACK arrives) are excluded -- k changes only via clean-ACK arrivals and fresh_pop draws, nothing else.
Conclusion: the ≤3-valid-EV claim holds. Cause: k is a running sum (each clean ACK is +1, each fresh_pop draw is -1) against a fixed ~84ns SEND-to-SEND line-rate cadence. A mean of ~1 ACK per window is expected by conservation (every packet is ACKed once) and does NOT contradict k≥4 -- about 19-21% of windows receive 2 ACKs instead of 1 (the distribution below), and k climbs to 4-5 when a couple of these 2-ACK windows land back to back, not from any single window receiving many ACKs at once.
